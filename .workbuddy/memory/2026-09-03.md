# 2026-09-03

## hex-map-wfc 源码分析 + Godot addon 迁移路径评估（只分析，未改代码）

### 仓库性质
- fork 自 felixturner/hex-map-wfc（MIT），origin = github.com/guhuajun/hex-map-wfc
- Three.js WebGPU + TSL 的六边形 WFC 地图生成 demo，src 共 9690 行 JS

### 分层耦合结论（迁移决策的核心依据）
- **L0 纯算法 1501 行，零 Three.js 依赖**：SeededRandom(53) / HexTileData(249) / HexWFCCore(287) / workers/wfc.worker(745) / HexGridConnector(167)
- **L1 求解编排 ≈900 行**：WFCManager(288，仅耦合 App.log + worker 桥) + HexMap.js 内的 `_runWfcWithRecovery` / `_setupPopulateContext` / `populateAllGrids` / `addWaterEdgeSeeds` / `getMapCornerOceanSeeds`
- **L2 世界状态+装饰放置 ≈1000 行**：HexGrid 数据部分、Decorations/DecorationDefs 的噪声聚簇决策（混了 Object3D/Color/three SimplexNoise）
- **L3 表现层 ≈6300 行**：BatchedMesh、TSL 材质、Water(160)+WavesMask(384)、PostFX(342)、Lighting(173)、GUI(473)、App(643)、动画/Placeholder/Debug

### 迁移关键技术判断
1. **数据结构必须重写才有性能**：现用 `Map<"q,r,s">` + `Set<"type_rot_level">`。Godot 侧应改为 `Vector3i` 作 Dictionary key，state 打包成 int（type*30+rot*5+level，900 状态），possibilities 用 900-bit bitset（15×int64），byEdge 索引预计算成掩码 → propagate 变位与运算。
2. **确定性靠 Mulberry32**（SeededRandom.js）。**不能用 Godot 的 RandomNumberGenerator（PCG32）**。移植需手动 32 位掩码 + imul 截断，并做逐位对照测试。
3. **SimplexNoise 来自 three/examples**，若要跨引擎同 seed 同地图必须一并移植（FastNoiseLite 输出不同）。
4. **BatchedMesh 在 Godot 无等价物** → 每种 tile mesh 一个 MultiMesh（约 30 draw call，与现状 38 同量级）；instance color 传 level 应改用 `INSTANCE_CUSTOM`。
5. **PostFX 342 行基本可弃**：Godot WorldEnvironment 自带 SSAO/DOF/Glow，只需补 film grain。手写 frustum-fitted shadow map 可用 DirectionalLight3D PSSM 替代。
6. **WavesMask 的 RT 膨胀+模糊管线不要照搬**：地图是离散六边形格，海岸距离场可在 CPU 上用 BFS 解析计算后写入 ImageTexture，比 SubViewport 链更简单更准。
7. **Web Worker 协议很干净**（init/solve → result），可直接映射 WorkerThreadPool；或改写成分帧协程，顺带白拿逐格生长动画（现在靠 collapseOrder + GSAP 事后补）。
8. **迁移前应先在 JS 侧重构**：把 HexMap.js(1751 行) 里的纯逻辑抽成 HexWorldModel，用现成的 `runBenchmark` / `runBuildAllBenchmark` 验证等价，可把移植风险降一个数量级。

### 方向性提醒
本 repo 是 3D WebGPU 视觉 showcase，与项目"2D + 资源受限 + Opus Magnum 式离散谜题"纪律冲突。推荐只做 L0+L1 的算法内核 addon，表现层用 Godot 原生 2D，不要 1:1 复刻 3D 效果。

### 关键教训（避免重蹈 40 分钟打转）
- **等价性证明不要用 `eval` 从 git 抽旧方法+手写 WFCManager 表面+双世界编排**：三个自制子系统各自脆弱，复杂度超过被测代码，且"OLD"端本就含手写重实现，并不比"逐字搬移"更可信。正确做法：①`git diff` 审计确认方法逐字搬移（本任务已确认）；②直接对真实 Model 跑确定性/一致性测试。
- **host 方法名必须严格匹配模型调用**：模型调 `this.host.solveWfcAttempt`，手写 host 若误命名为 `runWfcAttempt` 会报"is not a function"。诊断时务必查**模型实际调用的那个属性名**，否则容易把"属性名不一致"误读成对象身份谜题，在测试桩里空转。
- 单次中心网格求解 ≈1s（半径8→217格）；50 种子×12 网格×2 次 ≈10 分钟，CI/本地跑需放后台或调 SEEDS 环境变量（默认 15）。

### 等价性测试最终结果（后台跑完）
- `SEEDS=50 node tools/equiv-test.mjs`：50/50 种子全部 `OK`（0 FAIL，EXIT=0），打印 `✅ PASS`。
- 验证覆盖：每个种子跑两遍（A/B），同 seed 两次字节一致（确定性）；每格 tile type/rotation/level 合法（一致性）；全程无异常。
- 结论：重构后的 `HexWorldModel` 在真实 `HexWFCSolver` 下行为保持，移植可靠性已被"git diff 逐字搬移审计 + 50 种子确定性运行"双重坐实。
